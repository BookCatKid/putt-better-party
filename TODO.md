# Better Party development backlog

Review baseline: `b7c4d28` (2026-11-17). This is the implementation and review checklist for the next development pass. It records known defects, verification gaps, proposed features, and deployment prerequisites separately. A proposed feature is not evidence of an existing bug.

## Working agreement

- [ ] Read `AGENTS.md`, `docs/architecture.md`, `docs/development.md`, this backlog, and the current Git diff before editing.
- [ ] Work in logical, reviewable commits. Update this checklist as tasks are completed, with evidence in commit messages or a concise implementation report.
- [ ] Keep the independent Better Party backend and the original putt.day game client. Do not replace the engine or rely on the official party backend.
- [ ] Reverse-engineer available original bundles, WASM and relevant binary dependencies before changing compatibility behavior or making protocol test requests. Establish the actual call paths and data contracts. Do not infer correctness merely from successful requests.
- [ ] Preserve the approved home, join and rejoin layout, original in-game UI, original favicon, and actual community-browser card design. Do not invent decorative UI or generic substitutes.
- [ ] Use live public community courses. Do not bundle, permanently cache or maintain a separate playable course collection. Metadata and bounded process-local validated specifications are acceptable.
- [ ] Preserve all existing functionality, including unlimited manual playlist length, duplicates, random history, custom settings, host controls and scorecards. Resource limits must not silently reintroduce a nine-hole manual playlist cap.
- [ ] Keep handwritten code readable, descriptive, formatted, linted and typed. Keep exact upstream anchors and ABI aliases isolated from authored implementation. No lint/type suppressions or unnecessary abstractions.
- [ ] Keep the repository private. Do not commit downloaded client assets, room databases, HAR files, credentials, recordings or logs. Do not publicly deploy without authorization and asset-rights review.
- [ ] Run relevant unit, protocol and real-browser regressions after each subsystem change. Never weaken assertions, remove tests or hide failures to obtain a green result.
- [ ] Use isolated rooms, database paths, browser profiles and ports for tests. Do not interrupt the live local service or other agents' work without coordination.
- [ ] Obtain approval for major product-policy changes (e.g. elimination rules, host succession policy, account system, public deployment). Optional features below are proposals, not permission for destructive changes.
- [ ] End with a clean working tree, exact commit range, completed/uncompleted checklist, test results and known limitations. Do not claim every possible bug is fixed.

Priority: P0 = correctness or prerequisite; P1 = important improvement; P2 = optional expansion. "Verify" means establish evidence before deciding whether a code change is needed.

## 3. Host and player management

- [x] **P0 — Host transfer.** (Authoritative, single-step hand-over. `Room.transferHost` moves `hostUid`, rotates `hostToken`, records `hostTransfer` (from/to/timestamp) and tells both sides over their own authenticated sockets: `host-granted` carries the new capability to the new host and `host-revoked` goes to the old one, whose stored token is then dropped. A transfer needs no round identity, so it works in the lobby and between rounds, and it is refused for an absent, disconnected, self-named or non-host requester. The client adopts or drops the capability in the transport, keeps the join-frame copy in step for reconnects, and the roster crown moves in the same snapshot every client receives. Authorization stays token-bound: `/api/import` checks the presented capability against the live `hostToken`, so the old host's copy returns 403 afterwards (proven end to end). Host panel offers connected players under "Make someone else host"; spectators are only offered when nobody else is connected. Regressions: 5 room tests (atomic move + roster + both frames + rotated capability; refusals; no round identity needed; spectator last resort; hand-over record persisted with ownership across restart) and 2 transport tests (granted adopts/revoked drops while preserving the lobby count; a reconnect claims with the current capability rather than a stale one). Live protocol proof in `tests/integration/check-room-lifecycle.mjs` and browser proof `tests/integration/check-host-transfer.mjs`, which moves the crown mid-round between two real clients, extends the timer from the new host, ends the party from it and drives the old host's controls out of existence. Commit `<pending>`.)
- [x] **P0 — Host succession.** (Deliberate departure and temporary outage are now different events. A dropped host connection arms `HOST_SUCCESSION_GRACE_MS = 30_000` rather than moving the crown, so a refresh, a tunnel or a brief network blip keeps the party with its host; a host that returns inside the window cancels the pending succession (`clearHostSuccession()` on `claimsHost`). A deliberate `t: 'leave'` frame, sent only from the explicit "Leave party" control, promotes immediately, because the departure is unambiguous; adapter teardown deliberately does not send it, since the route also unmounts on re-subscribe. Successor selection is the first connected candidate in join order, preferring players over spectators and falling back to a spectator only when no player is left, so an elimination round cannot leave the party hostless. Promotion rotates the capability and delivers it over the successor's socket, and `hostUid`/`hostTransfer` are checkpointed and restored so a restart does not resurrect the old owner. Regressions: 5 room tests (immediate promotion on deliberate leave; outage arms a timer instead of moving the crown; a returning host keeps the party and no successor is announced; promotion picks the longest-present connected player and the promoted host can act; spectator only as a last resort; persisted ownership and hand-over record survive a restart). Verified 3 of them fail with succession disabled. Browser proof of the deliberate-departure path in `tests/integration/check-host-transfer.mjs`. Commit `<pending>`.)
