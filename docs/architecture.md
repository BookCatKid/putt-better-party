# Architecture and operation

The HTTP service exposes room creation, session issuance, catalog browsing and course retrieval. The independent WebSocket room state machine owns admission, host permissions, round timing, progression, elimination and standings. The original client handles rendering and simulation.

## Course selection

Manual playlists contain public course IDs. Maps are fetched and validated from the public API as needed; no playable map is stored permanently. Random selection tracks per-room history and avoids repeats until the available pool is exhausted. The daily exclusion option refreshes every page of public featured-hole metadata at the beginning of each random match. Random selection draws only as many positions as are still needed and overlaps independent page reads, then processes their results in draw order. Every randomly selected specification must still pass the original validator before the match starts; manual playlists still load later holes on demand. Public catalog reads share a FIFO queue with at most three in-flight requests and a minimum 350 ms interval between starts. The interval is a local protective pacing choice, not a documented upstream rate limit.

Optional course voting is available for randomized matches, off by default. Every hole, including the first, has three distinct, validated public options prepared with the same daily exclusion and no-repeat rules. The room remembers all offered courses in its random history, even when not selected. A 15-second ballot opens before the first countdown and after each subsequent round of results; every connected identity (including spectators) has one revisable vote. New arrivals during the first ballot may join the first hole regardless of the mid-match admission policy. Votes from disconnected identities do not count unless the identity reconnects. The next course is drawn randomly with probability proportional to its vote count: each vote is one ticket. Unvoted options have zero chance if any votes exist; with no votes, all three are equally likely. Future options are prevalidated (three details per hole), so opening the ballot does not need to fetch playable geometry. This increases initial preparation time compared with ordinary random matches. Ballot updates are scoped to a unique vote ID and send only the voting state, not course geometry.

Custom playlists can be generated from a combination of title/maker search, minimum and maximum rating, rating count, par, average strokes, difficulty (average strokes minus par), and inclusion or exclusion of previously featured daily holes. All chosen constraints must match. The public stats GET is identified in the pinned client: the community holes route imports index export K, bound to Ja, which invokes the same function as the public HoleStats panel with only the course ID. The server projects average strokes only; it does not request or expose admin-only exact completion statistics. Par is obtained from the public detail and the original validator. Ranges requiring unavailable measurements exclude those courses; there is no inferred upstream difficulty field. Scans use the same paced public read queue as other catalog requests and traverse the complete supported pagination range. They fail rather than silently truncate if completeness cannot be established, and a catalog is not a transactional snapshot. One cancellable scan may run at a time to avoid overwhelming the public service; it publishes the matching IDs only after success, keeping the current playlist intact on failure, cancellation, or no matches. The host can choose replacement or unique append, catalog ordering or shuffle, and an optional maximum course count. The maximum is applied after scanning, filtering and ordering the full candidate pool, so shuffled selections sample the entire pool rather than only its first page. In append mode the maximum counts newly selected courses; existing playlist IDs are excluded before selection. Only metadata is retained for generated playlists; playable specifications are fetched and validated when needed. Numeric filters requiring per-course data may be considerably slower than list-only filters.

The lobby preserves the original generated course scene and player indicators, with a responsive two-column grid of aligned settings panels. Long player lists scroll within their panels. The playlist editor opens in a separate dark, rounded modal, which keeps the lobby compact and retains the existing browsing, generation, ordering and saved-playlist operations.

## Room lifecycle

SQLite retains room settings, public playlist metadata, random history and private session credentials. On restart, interrupted matches recover to their lobbies because browser-local physics state cannot be reconstructed. Unoccupied rooms expire after 30 minutes. A same-document reconnect retains progress; a full reload during an active unfinished round forfeits that hole. The server’s round timer continues during connection interruptions. The original server-side session replacement close reason is handled explicitly: when another tab claims the same identity, the displaced tab stops reconnecting and offers a return home or manual reload.

The host chooses a late-join policy in the lobby. Never permits watching but not playing until the next match. After current hole puts first-time arrivals into the next hole that begins, provided the match continues; restarting the same hole does not admit them. Always (the default for new rooms) admits first-time arrivals during countdown or play using the existing round deadline, or at the next hole if they arrive on results. Missed holes have no score rows and no penalty, with the existing holes-survived-first ranking retained. Eliminated identities and identities that deliberately leave cannot use late admission to restart their attempt. Regular reconnect and reload/forfeit rules are unchanged. Spectating removes the local rigid body and aim/shadow meshes, preserves other players and uses the original free camera.

Admission capacity is checked both when a credential is issued and again when its socket joins, so a credential issued before the room filled is still rejected at admission. Spectators count toward the maximum-player limit. Returning connected players keep their slot when the host reduces the limit, and no one is evicted; the host token by itself does not grant a slot — it only matters when the joining identity actually claims or retains host authority.

## Scoring and host controls

Non-finishers are eliminated in elimination mode. Without elimination, unfinished holes incur a penalty of at least par plus five strokes. Exact upstream ranking and penalty parity is not established. The server records elapsed milliseconds from the shared start of each hole until it receives an accepted completion or forfeit message. The timing includes network delay, and late entrants share the original start time. It is not client-submitted or independently physics-verified. The live count-up display freezes at the recorded completion time, while scorecards retain strokes and time for every scored hole. Stroke-play timeouts score the full allotted round duration, including extensions; otherwise eliminated or interrupted attempts retain their elapsed time as unscored diagnostics. Ranking preserves holes survived, alive status, and total strokes, then uses lowest total scored time, and finally name. Skipped and restarted attempts contribute neither strokes nor time.

Hosts can extend the current round by 15, 30 or 60 seconds up to 15 minutes. Skipping voids the hole; restarting resets its attempt and preserves previous scores. Ending retains completed scores without penalizing unfinished players. All commands are checked by the backend.

## Public leaderboard

The public leaderboard at /leaderboard stores each display name's best stroke total for each random-match length (1–9 holes), using lowest cumulative elapsed time to break equal scores. SQLite persists independent best-score records across room eviction and server restarts. Records are written at game finalization only when the full configured number of consecutive rounds was completed, and the player has a successful score and recorded time for every hole. Custom playlists, restarted attempts, skipped or interrupted rounds, timeout/elimination, and late entries that missed any holes are ineligible. Random course voting remains eligible. The public page lists and searches records by display name and hole count, preserving overall rank in search results. Names are normalized for case and Unicode compatibility, not authenticated accounts; users sharing a display name share a record. Scores are client-reported, not server-verified physics. The board begins recording at feature deployment rather than reconstructing historical matches from incomplete event logs.

## Deployment considerations

The service is intended to operate independently of putt.day's official party servers. Public course availability depends on the pinned upstream read protocol. Before exposing a service publicly, obtain any needed asset redistribution permission and review authentication, abuse prevention, rate limits and deployment security. Client-reported scores are not server-verified physics.

## Client initialization

The original game component must mount before its WebSocket connects. The party route keeps that component mounted but suppresses its incomplete HUD until the authoritative snapshot, local player roster entry, scoreboard, accepted map and original scene preparation callback are available. Final results also require the final standings message. The original scene preparation includes its upstream fallback timeout; this is not a guarantee that every GPU or asset has loaded successfully.

The party socket adapter lives in `scripts/party-transport.js`, with its original bundle bindings in the patcher. It waits for a synchronized snapshot, roster and board before enabling commands, retries interrupted connections with bounded exponential backoff, and cleans up its timers and subscriptions on exit.

## Administration

The read-only `/admin` dashboard provides live room and player status, current and completed holes, scores, and the most recent 500 gameplay events (bounded log tails, not an all-time history). It refreshes every five seconds while visible. Enable it by configuring a Bun-compatible Argon2id hash in `BP_ADMIN_PASSWORD_HASH` in the server's private environment. Without a hash the admin API is disabled. The password is never sent to the gameplay log or included in the client bundles. The admin API uses expiring in-memory sessions in HttpOnly, SameSite=Strict cookies (Secure on HTTPS), validates POST origins, and throttles failed logins globally. Sessions are invalidated by a restart. No administrator write operations or access to upstream administration are exposed.
